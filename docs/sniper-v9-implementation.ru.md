# Bullseye 0.2.0: исправления и новый paper baseline

Дата: 13 сентября 2026. Основание — `profitability-audit-2026-09-13.ru.md`.

Исправлены технические источники искажения результатов и изменена проверяемая
политика торговли. Положительное математическое ожидание ещё не доказано.
Параметры ниже — гипотеза для отдельного forward-теста, а не оптимум,
найденный на надёжном историческом replay.

## Что изменилось

| Проблема | Реализация |
|---|---|
| Позиция существовала до будущего `filled_at` | Автоматическое и ручное исполнение ждут задержку, обновляют рынок и используют фактическое время. Симулятор отвергает исполнение раньше полной задержки. |
| Поздний вход по устаревшему сигналу | Возраст сигнала до 5 секунд, повторная проверка после ожидания, допустимое изменение текущей reference price за ожидание до 8%. |
| Стоп по средней цене чужой сделки | Feature engine, позиционная оценка и outcomes используют marginal reserve price при наличии резервов. RPC-monitor и trade handler вызывают общую exit policy. |
| Выход по цене, которая уже восстановилась | Перед продажей повторно читаются резервы, позиция и controls, затем заново проверяется выход. Восстановление цены также отменяет мягкий hazard. |
| Ошибки порядка событий | Mark watermark не допускает обновлений до входа и поверх более новой оценки. |
| MAD превращал небольшую продажу в экстремальную | Вместо 999 используется ограниченный снизу масштаб. Outlier требует материального размера и доли ликвидности, а также подтверждения потоком/ценой/резервами. |
| Hazard проверялся только на редких snapshots | Для каждого обработанного trade доступен текущий snapshot независимо от частоты сохранения. Hazard подтверждается во времени; прибыльная позиция не закрывается только из-за него. |
| Ранний trailing обрезал продолжение | Runner включается после +50%, ширина 18–30% от максимума, растёт с достигнутым движением; половина фиксируется при +100%. |
| Score выглядел увереннее доступных данных | Risk/lifecycle/market больше не дают вес доходности. Wallet/social имеют нулевой вес. Momentum 70%, graduation velocity 30%; второй компонент недоступен без резервов и buyer attribution. |
| Холодное окно выглядело ускорением | Ускорение не учитывается до накопления половины окна; вход дополнительно требует достаточного времени наблюдения. |
| Входы по нескольким адресам/сделкам | Balanced требует 10 trades, 6 buyers, 15 секунд наблюдения, минимум 80% buyer attribution, долю крупнейшего покупателя не выше 50%, положительный flow и наблюдавшиеся продажи без отрицательного изменения цены за окно. |
| Разные стадии смешивались | Balanced/Aggressive работают на кривой; Conservative проверяет post-graduation/mature continuation. Это разные версии пресетов; одновременно исполняется один. |
| Слабая политика концентрации | RPC gate: top-1 <35%, creator <20%; неизвестная доля creator блокирует вход. Alpha blocking включён для известных holder/deployer нарушений. |
| Virtual reserves считались настоящей ликвидностью | Кандидаты калибруются через RPC; offsets virtual–real используются для обновления real reserves. Начальный запас проверяется по create event. При отсутствии данных progress не придумывается. Он может уменьшаться при продажах. |
| Сделка могла расходовать виртуальную ликвидность | Проверяется доступность real token/SOL reserves; complete curve не исполняется. При миграции используется текущий market, старые curve reserves не переносятся в pool. |
| Impact включал другие расходы | Отдельные поля для AMM impact и полного отклонения цены. Комиссии, network/priority cost и slippage сохранены. |
| Уменьшение размера фактически не работало | Minimum ticket отделён от target. Размер ограничен риском 0,5% капитала и резервом потери 30%; при капитале 100 USDT типичный верхний target около 1,67 USDT до расходов. Он может быть уменьшен или отклонён. |
| Слишком дорогой round trip | Balanced допускает оценку полного цикла до 7%, Aggressive — до 9%. Это потолки модели, а не измеренные фактические комиссии. |
| Слишком узкое наблюдение | Очередь свежих кандидатов, до 4 одновременных наблюдений, 60 секунд, базовый cap 24 trades; подтверждённый интерес продлевает наблюдение до ограниченного cap 96. |
| Задержки исполнения мешали потоку trades | Торговая обработка вынесена в ограниченную очередь с объединением событий по mint; исходные trades сохраняются отдельно. RPC-калибровка и запись БД всё ещё занимают время. |
| После выхода терялся путь цены | Ограниченные research subscriptions: до 8, срок 3660 секунд; 10% контрольной выборки rejected/watch mint выбирается стабильным hash. Lease восстанавливается из БД. |
| Отсутствие данных маскировалось под результат | Horizon имеет coverage и допустимое опоздание до 10% горизонта, максимум 60 секунд. Gap не получает доходность; post-exit не переписывает реализованный PnL/MFE сделки. Отчёт показывает missing/pending и legacy-unverified. |
| Настройки менялись внутри эксперимента | Snapshot содержит кодовый SHA-256, параметры исполнения и controls. Несовпадение останавливает новые входы. |
| Запуск зависел от всего архива | Восстанавливаются недавние рынки и открытые позиции. Последний lifecycle выбирается одним SQL-запросом вместо запроса на каждую монету. |

## Окончательная конфигурация

- Эксперимент: `sniper-v9-forward-2026-09-13`, новый портфель 100 USDT.
- Основной пресет: Balanced v9, ранний спрос с подтверждением продаж.
- Stop: −12%; первый TP: +100%, продажа 50%; runner: активация +50%, trailing 18–30%.
- Максимальное время обычной позиции: 1800 секунд; достигшего runner-уровня: 7200 секунд.
- Stagnation: 120 секунд, если MFE <5% и текущая доходность неположительная.
- До 5 позиций; общий daily loss governor и cooldown сохранены.
- Общий PumpPortal budget **не увеличен**: 5000 trade events в сутки. Часть зарезервирована для открытых позиций; при исчерпании лимита остаётся RPC-monitor.
- `.env` обновлён без изменения ключей. Старые портфели и сделки сохранены. Два промежуточных эксперимента остановлены; они не содержат исполненных сделок.

## Проверка и запуск

Проверено: 125 тестов, Ruff, mypy; миграция PostgreSQL до `20260913_0015`.
Регрессионные проверки включают задержку, stale snapshots, tiny-sell hazard,
subsecond features, real liquidity, trailing, drift и post-exit coverage.
Ограниченная проверка живого потока выполняется с paused entries и без уведомлений.
Она не является тестом доходности. Логи: `sniper-smoke-r2.log` и `sniper-smoke-final.log`.

В рабочей папке:

```powershell
.venv\Scripts\python.exe -m memebot entries-resume
.venv\Scripts\python.exe -m memebot discover
```

Запустить панель отдельно, если она ещё не запущена:

```powershell
.venv\Scripts\python.exe -m memebot telegram
```

Вместо `entries-resume` можно включить Resume в панели. До этого входы намеренно
paused; worker из проверки завершается и не остаётся фоновым процессом.
После Resume paper-входы будут автоматическими, если кандидат пройдёт фильтры.
При изменении торговых controls или исходников потребуется отдельный эксперимент.

```powershell
.venv\Scripts\python.exe -m memebot experiment-report --name sniper-v9-forward-2026-09-13
```

## Что ещё требует данных

Без достаточного покрытия нельзя доказать, что более поздний выход лучше,
оценить executable 2x/5x или обучить вероятность прибыли. Старые 35 сделок
не восстанавливают пропущенные пути цены. Наблюдения после выхода — mark prices,
а не обещание возможности продать весь размер по максимуму.

Runner использует ограниченную эвристику ширины по достигнутому росту;
это пока не volatility model. Адреса покупателей не равны независимым людям.
Funding graphs, полноценная bundle attribution и независимая wallet reputation
не были добавлены как выдуманные сигналы: их недоступность остаётся явной.
Известные cohort-нарушения блокируют; неизвестный сторонний holder profile
не подменяет обязательные RPC-проверки.

Бюджет наблюдения ограничен, eviction и провайдерские сбои дают цензурированную
выборку. В отчёте `missing_or_pending` объединяет ещё не наступивший горизонт
и отсутствующее наблюдение; это не нулевая доходность и не доказанный убыток.
Первый этап — накопить новую серию по неизменной версии и смотреть net expectancy,
profit factor, drawdown, costs, уникальные mint и coverage. Сравнение сетапов
и настройку выходов проводить на последующих временных отрезках, сохраняя
отдельный период для проверки. Простое повышение score или ослабление стопа
не заменяет эту проверку.
